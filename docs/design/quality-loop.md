# 品質ループ（受賞水準までの自己検証手順）

> 2026-10-09 作成。`v2-launch.md` の Phase 8 で実行する。実装者（Opus）は本書の手順で**自分の成果物を採点し、合格条件に達するまで修正を繰り返す**。
> 採点は甘くしない。根拠（スクリーンショットのパス、計測値、axe の出力）のない加点は無効。

## 1. 基準

Awwwards の配点（Design 40 / Usability 30 / Creativity 20 / Content 10）を主軸にし、Webby の 6 軸と FWA の「初見の驚き」を補助軸として使う。開発ゲートは pass/fail。

### 1.1 採点軸（各 10 点満点、小数 1 桁）

| 軸 | 重み | 10 点の姿 | 6 点の姿（不合格） |
|---|---|---|---|
| Design | 40% | 活字・余白・色・グレインが一つの声で語る。どの画面を切り取っても「このサイト」と分かる。カテゴリ色のにじみが品よく効く | shadcn のデフォルトが透けて見える。見出しが小さい。白いカードが並ぶだけ |
| Usability | 30% | 3 クリック以内に任意のパターンへ。⌘K が速い。モバイルで親指だけで完結。読みやすい行長 | 目次がない、ハッシュ遷移が外れる、デモが画面幅を超える |
| Creativity | 20% | X-ray モードと Living Wall が「自己言及」というコンセプトとして伝わる。ページ遷移に連続性がある | 演出が飾りで、コンセプトと結びつかない |
| Content | 10% | 341 件の説明が揃い、notes が実装者目線で具体的。未検証情報が出ていない | 説明が 1 語、notes が空、unverified が見える |

補助軸（Webby）: Structure & Navigation / Visual Design / Functionality / Interactivity / Overall Experience。各 10 点。
FWA 軸: **初見 5 秒の驚き**（ヒーローを見た瞬間に「触りたい」と思えるか）。10 点。

### 1.2 開発ゲート（すべて pass が必要）

| ゲート | 条件 |
|---|---|
| G1 lint / typecheck / test | エラー 0。警告も 0 |
| G2 build | `output: "export"` で成功。`out/` の HTML が 341 + 40 ページ |
| G3 コンソール | 全ルートで error 0 / warning 0（recharts 警告も不可） |
| G4 Lighthouse（モバイル） | Performance / A11y / Best Practices / SEO すべて ≥ 95。ホーム、カテゴリ 1 つ、パターン 1 つ、目的 1 つの 4 ページ |
| G5 Core Web Vitals | LCP ≤ 1.8s、CLS = 0、INP ≤ 200ms（Lighthouse の値で可） |
| G6 予算 | `v2-launch.md` §6.2 の JS / フォント予算内 |
| G7 axe | 代表 8 ページで serious / critical 0 |
| G8 キーボード | Tab だけでホーム → ⌘K → パターンページ → ステージ切替 → 戻る、が完了する |
| G9 reduced-motion | エミュレートして全ページを開き、自律アニメーションが止まっていること |
| G10 モバイル | 390 幅で横スクロールなし、タップ目標 44px 以上、ステージ内デモが崩れない |
| G11 ステージ両対応 | 全デモがライト/ダーク両ステージで読める（スクリーンショットで確認） |
| G12 デモ規約 | `v2-launch.md` §5.2 の 9 項目を全デモで満たす（チェックリスト表を `docs/qa/demo-checklist.md` に残す） |

### 1.3 合格条件

- 採点軸: Design / Usability / Creativity / Content すべて **≥ 8.5**、補助軸すべて ≥ 8.0、FWA 軸 ≥ 8.0。
- ゲート G1〜G12 すべて pass。
- **2 ラウンド連続**で「新規の指摘ゼロ」かつ上の条件を満たす。
- 上限 10 ラウンド。上限に達したら残課題を `docs/qa/remaining.md` に書いて停止し、人に判断を返す。

## 2. ラウンドの手順

各ラウンド N で以下を順に行い、`docs/qa/round-N.md` に記録する。

### 2.1 計測

```sh
pnpm run check          # G1, G2, G7 の一部
pnpm run shots          # 1440 / 390 × dark stage / light stage × motion / reduced-motion のスクリーンショット
pnpm run lhci           # G4, G5, G6
```

スクリーンショット対象ルート（固定）: `/`, `/categories`, `/c/data-visualization`, `/c/motion`, `/p/contribution-heatmap`, `/p/command-palette`, `/goals`, `/g/experience`, `/not-found`、および ⌘K を開いた状態、X-ray ON のホーム。

### 2.2 自己採点

1. スクリーンショットを**すべて開いて見る**。見ていない画面は採点しない。
2. §1.1 の各軸を採点し、各軸に根拠を 2 つ以上書く（「ヒーローの見出しが 1440 幅で 96px、余白が 160px で呼吸している: shots/home-1440-dark.png」のように）。
3. ゲート表を埋める。計測値を数字で書く。
4. 「指摘」を重大度（S: 公開不可 / A: 受賞を妨げる / B: 磨き）付きで列挙する。各指摘に画面と再現手順を付ける。

### 2.3 外部視点の採点（必須）

自分の採点だけでは甘くなる。**毎ラウンド、文脈を持たない別エージェント**（Agent ツール、general-purpose）に以下だけを渡して採点させる:

- 本書 §1 の基準
- そのラウンドのスクリーンショット一式
- `pnpm run lhci` の出力

渡さないもの: 自分の採点、実装の経緯、言い訳。別エージェントの採点が自分の採点より 1.0 以上低い軸は、**低い方を採用**する。

### 2.4 修正

- S → A → B の順で直す。1 ラウンドで直す数に上限はないが、直したものは必ず次ラウンドのスクリーンショットで再確認する。
- 修正のたびに該当ゲートを再実行する。
- 「直すと別の軸が下がる」場合は、下がる軸と理由を round-N.md に書く。

### 2.5 コミット

ラウンドごとに 1 コミット。件名は `qa: round N — <主な修正>`。Claude 由来のトレーラーは付けない（ユーザー方針）。

## 3. 参照の使い方

受賞サイトの「作法」を学ぶために、Awwwards の SOTD（Site of the Day）を **3 件以上**、実際にブラウザで開いて次を観察し、`docs/qa/references.md` に記録する。クローンはしない。

- ヒーローの見出しサイズ（px）と余白の比率
- ホバーの反応時間とイージング
- ページ遷移の種類と長さ
- モバイルでの崩れ方（崩れていない理由）
- 読み込み中の見せ方

観察した値のレンジを自サイトの値と並べ、外れているものは根拠をもって変えるか残す。

## 4. やってはいけないこと

- 計測せずに「十分速い」と書く。
- スクリーンショットを見ずに採点する。
- 指摘を「仕様です」で閉じる（本当に仕様なら `v2-launch.md` の決定番号を引く）。
- ゲートを緩める。緩めたくなったら、理由を `docs/qa/remaining.md` に書いて人に返す。
- 演出を足して Usability を落とす。Design と Creativity の点は Usability を犠牲にして取らない。
- 外部スクリプト・外部フォント・外部画像を足す（`v2-launch.md` D12）。
