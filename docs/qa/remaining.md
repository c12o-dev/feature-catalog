## R1 フォント予算 120KB（G6）— ホーム以外で超過

- 和文 3 書体（D3）× ページの文言量で、ページごとに本当に必要な量がすでに 80〜100KB ある。
- 現行の方式（`scripts/fonts/subset.py`: 共通 / ホーム / 索引群 / カテゴリ別のスライス）だと、ホームは 124KB、他は 180〜360KB（Fontsource のスライスは 550〜790KB）。
- 共有スライスを最適化するやり方（使用ページの組み合わせごとに貪欲マージ）も試した。それでも 1 ページ 190KB 前後から下がらない。カテゴリページの文言がカテゴリ横断で散っているため。

選択肢:
1. **ページごとの専用サブセット**（共通 core + ページ差分）。全ページ 120KB 以内に入る見込み。代わりに生成フォントが約 10MB 増え、それをコミットする（文言を変えるたびに差分が出る）。ソフト遷移では `:root:has([data-fonts=…])` で書体ファミリーを切り替える。
2. **予算をページ種別で分ける**（ホーム 120KB、その他 300KB など）。quality-loop §4 では、ゲートを緩めるには人の承認が要る。
3. **本文を Zen Kaku からシステムの和文フォントに変え、明朝見出しだけ自前にする**。D3 の変更にあたる。

## R2 CLS = 0（G5）— フォント swap による揺れ

- 揺れの原因は 4 ページともフォントの差し替え（Lighthouse がフォント読み込みを原因に挙げている）。値は実行ごとに 0〜0.037。
- `font-display: optional` にすれば 0 になる。ただし初回訪問は回線によってはフォールバック書体のまま表示される（2 回目以降はキャッシュで本来の書体）。
- フォールバックの寸法合わせ（`size-adjust` / `ascent-override`）は、OS によって代わりに使われる書体が違う（Hiragino / Yu Gothic / Noto）ため、0 までは詰められない見込み。

選択肢: (a) `optional` にする、(b) swap のままにし、寸法合わせで小さくした値を許容する。

## R3 Perf ≥ 95 / LCP ≤ 1.8s

- 主因は Slow 4G 相当の帯域でのフォントと JS の転送と、hydration。R1 が解決すれば LCP も縮む見込み。
- 打った手: 検索インデックスの静的 JSON 化、⌘K の遅延読み込み、motion の除去（ホーム）、画面外カードへの content-visibility、opacity 0.01 からの入場。
